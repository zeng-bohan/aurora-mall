## 4. 修复记录

| 编号 | 严重度 | 问题 | 根因 | 修复 |
| --- | --- | --- | --- | --- |
| F1 | P0 | 部分退款把支付单记成 `REFUNDED`，后续退款无法结算 | MySQL 单表 UPDATE 按从左到右赋值，`status` 读到累加后的 `refunded_amount` | `PaymentOrderMapper.applyRefund` 先算状态再累加金额 |
| F2 | P0 | 退款记录插入后支付累加失败会留下孤儿记录，重试直接返回“成功” | 插入与累加不在同一事务，重复请求先查退款记录 | `PaymentService.internalRefund` 用事务包住插入与累加，失败整体回滚；重复/并发用唯一键裁决并校验订单与金额 |
| F3 | P1 | 同一幂等键重试在下单后商品下架或券已核销时失败 | 幂等映射在商品、券校验之后才查询，指纹还包含实时价格 | 先按稳定指纹回放，再加载商品/券；指纹只含地址、券和排序后的 SKU/数量 |
| F4 | P1 | 部分退款后明细优惠之和大于父订单优惠 | 已退商品保留原分摊，剩余商品又被分摊整张券 | 已退明细优惠置零，剩余明细重新分摊整张券 |
| F5 | P1 | Redis 已扣库存但 DB 台账回滚后订单永久卡死；已释放台账无法修复 Redis | 补偿失败无重试入口，释放只看 `RESERVED` 台账 | 预扣重试按请求重建台账；释放对已 `RELEASED`/台账缺失也重试 Redis；新增运营台“重建 Redis” |
| F6 | P1 | 退款回补 DB 成功、Redis 失败后无法补偿，可能重复加库存 | 回补没有 Redis 幂等守卫，失败只记日志 | 新增退款级 Lua 守卫；DB 已回补时重试只修 Redis，不重复加库存 |
| F7 | P1 | 秒杀归还 Redis 失败只记日志，库存长期少算 | Redis 同步在 DB 事务外且无幂等凭据 | 新增订单级归还守卫；同步失败抛出让关单/退款结算重试 |
| F8 | P1 | 登出只拉黑当前 access token，其他会话 token 可用到过期 | 网关只查 jti 黑名单，没有读取会话失效时间戳 | 网关同时校验 `session-invalid-before`，登出后更早签发的 access token 全部拒绝 |
| F9 | P2 | 页面仍显示“领取”已领取的券，点击后报错 | 券视图没有模板 id，前端无法判断已领取 | `CouponView` 增加 `templateId`，券页面显示“已领取”并禁用 |
| F10 | P2 | 注册页允许 3 位用户名，后端要求至少 4 位 | 前后端规则不一致 | 前端校验和占位文案改为 4 位 |
| F11 | P2 | 商品编辑在事务提交前删缓存，分类/属性编辑完全不失效缓存 | 缓存失效时机和覆盖面不足 | 事务提交后双删；分类、属性、属性值编辑按受影响 SPU 失效 |
| F12 | P2 | 后台库存设置遇到 Redis 与 DB 有差异时永远失败，无法人工修复 | 管理员设置依赖 Redis CAS，差异键无人处理 | 新增显式重建入口，种子脚本自动同步；周期对账仍只补缺失键 |
| F13 | P1 | 退款金额可能基于加锁前的过期订单快照计算，与上一笔审批并发时超过剩余实付 | `apply` 在事务外计算金额，事务内只锁订单不重算 | 在父订单行锁内重新读取明细、重算退款额并落账 |

此外，本轮确认并保留了工作区中上一轮未提交的修复：购物车拒绝下架商品、退款/发货按父订单加行锁、退款金额按实际退款额分摊、支付金额校验、详情页库存实时刷新、运营秒杀列表保留历史活动、库存释放失败转业务错误、refresh token 使用 SETNX 原子轮换。每项都通过本轮测试或浏览器操作复验。

## 5. 业务一致性结果

### 订单、支付、退款

- 多商品只生成一个父订单；支付金额与应付金额一致。
- 部分退款后父订单保持 `PAID`，支付单为 `PARTIALLY_REFUNDED`，退款金额与支付台账一致。
- 整单退款后父订单 `REFUNDED`，所有明细 `REFUNDED`，支付单 `REFUNDED`，优惠券回到账户。
- 结算失败时退款保持“已同意未结算”，重试后完成；重复审批不重复退款。
- 发货在待审批退款期间被拒绝；拒绝退款后明细恢复 `NORMAL`，可以继续发货。
- 关闭未支付订单/秒杀订单会释放库存；关闭后的迟到支付只退款，不确认库存。

### 库存

- 并发的最后一件库存只成功一次。
- 预扣成功后 DB 事务失败，库存释放并可在重试时恢复台账。
- 退款回补按退款单幂等，重复结算不会重复加库存。
- Redis 键缺失时按 DB 重建；有差异时运营可显式重建。验收结束时 45 个 SKU 的 Redis 与 DB 可售量完全一致。

### 秒杀

- 一人一单、售罄、未开始、活动结束时间窗均由 Lua 原子判断。
- 重复 MQ 投递只创建一个订单；落单失败归还名额，重复投递不会二次归还。
- 秒杀订单支付、关单和整单退款走统一订单流程；退款后活动库存回到原值。
- 运营创建、预热、列表历史活动均可操作。

### 优惠券

- 门槛判断按商品金额，券额按最大余数法分摊且总额守恒。
- 部分退款后剩余金额低于门槛时只允许整单退。
- 整单退款返还券；已领取券在前端不可重复领取。

## 7. 安全与权限

独立通过网关验证：

- 未登录访问受保护接口返回 401。
- 普通用户访问订单/退款/库存/秒杀/商品管理接口返回 403 或 404。
- 普通用户读取他人订单和退款报价返回 404。
- 客户端伪造 `X-User-Id`/`X-User-Role` 被网关覆盖，仍返回 403。
- `/api/order/internal/**`、编码点段和编码斜杠变体在网关返回 404/400，无法触达内部接口。
- 直连服务端口缺少内部密钥返回 401；健康检查保留。
- 支付 mock 回调缺少渠道签名返回 `40100`，签名校验通过后才落账。
- SQL 注入式关键词不造成异常或越权。
- 分页大小被限制在 50。
- refresh token 重放返回 401；登出后旧 access token 返回 401。
- 代码中未发现向日志输出密码、token 或内部密钥。

## 8. 未解决问题与边界

以下为已知边界，均不阻塞演示，也没有 P0/P1：

1. 定时任务与秒杀对账没有分布式锁，默认按单实例设计；多实例会重复扫描（操作幂等）。
2. 网关限流按路由共享配额，不区分用户/IP；登录接口没有独立的风控/锁定策略。
3. 运营端的用户、SKU、库存和商品列表未分页，适合当前 45 个 SKU 的演示规模。
4. 秒杀对账只有在 `PROCESSING` 超过处理超时后才补偿；极慢消费者超过 5 分钟时仍存在补偿与落单交叉的理论窗口。
5. 属性值的 TEXT/COLOR/NUMBER 类型是元数据，后端没有对值内容做语义校验（例如 NUMBER 值仍可保存任意字符串）。
6. 管理员删除 SKU 不会清理该 SKU 的库存行或购物车缓存；历史订单使用快照，不受影响。
7. 迟到支付退款是渠道原路退回，不写入 `payment_refunds`；演示一致性 SQL 对该场景单独放行。
8. 支付、物流是模拟流程，商品图是概念渲染，不代表真实商业服务。
9. `docs/m2`–`docs/m5` 的压测报告仍是重构前环境的数据，只用于对照。
